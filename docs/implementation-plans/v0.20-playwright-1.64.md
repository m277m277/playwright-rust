# v0.20: Playwright 1.64

Shipped in `playwright-rs` 0.20.0, `playwright-rs-trace` 0.2.1, and
`playwright-rs-macros` 0.1.2 on 2026-10-11. Kept as the record of how the
1.64 delta was established and supported.

Work tracking for moving the bundled driver from 1.63.0 to 1.64.0 and
supporting everything 1.64 added that a library binding can expose. The
upstream release is <https://github.com/microsoft/playwright/releases/tag/v1.64.0>
(2026-10-07); the tracking issue is #165.

## How the delta was established

The release notes are not the delta. 1.63 renamed every `tracingStart`
capture parameter without saying so, and this release changed the trace
format and the meaning of a request's `id` without saying so either. The
inventory below comes from four sources, each compared across the
`v1.63.0` and `v1.64.0` tags:

1. `git diff protocol-spec` after `cargo xtask sync-protocol-spec`, read with
   context so that events, initializers and `internal: true` markers count,
   not only added and removed lines.
2. `docs/src/api/*.md` in the Playwright monorepo and `types/types.d.ts` in
   the published `playwright-core` package, for the public API.
3. `packages/playwright-core/src/client` and `src/server`, for how each new
   method is implemented and for server behavior the spec does not show
   (the dispatcher, the trace recorder, `frameSelectors.ts`).
4. playwright-python `v1.63.0` against `main`, which already pins driver
   1.64.0 and implements every public `since: v1.64` entry. Its new tests
   are the behavior spec for the integration tests below.

Every method name the crate sends (182 distinct names across 223 send sites)
is present in the 1.64 `commands:` blocks (`cargo xtask
verify-protocol-methods`). The only commands removed are
`enableRecorder` and `disableRecorder`, and the only parameters removed are
`recorderMode` and `Metadata.stepId`; the crate uses none of them. The one
changed command the crate does send is `Frame.resolveSelector` (used by
`Locator::normalize`), which gained an optional `sdkLanguage` and an
optional `locatorCode` result. Neither matters to us: `locatorCode` is
computed only when `sdkLanguage` is sent, and the enum has no `rust` value.

## Slice 0: the bump

Landed in `afb350a`, closing #165.

- `PLAYWRIGHT_VERSION` in `build.rs`, the version test, the CI browser cache
  keys in `test.yml`, `release.yml` and `pages.yml`, the site's
  `PLAYWRIGHT_DEV` badge and its e2e check, and the `root.rs` note that the
  `sdkLanguage` enum was re-checked (it still has no `rust`). The README
  badge moves at release time, since it tracks crates.io.
- `protocol-spec/` synced; the result is byte-identical to a direct fetch of
  `packages/protocol/spec` at the tag.
- **Call ids are strings.** The 1.64 dispatcher takes a request's `id`
  verbatim as the call id it records in traces, where 1.63 wrote
  `` `call@${id}` ``. Our integer ids therefore came out as numeric
  `callId`s, which the trace format types as a string, and
  `playwright-rs-trace` turned every action event into `Unknown`. The
  connection now sends `abcd@7`, four random lowercase letters per
  connection plus the counter, which is what the JS client
  (`createCallIdGenerator`) and playwright-python main send. `Request::id`
  and `Response::id` in the `#[doc(hidden)]` `server` module are now
  `String`. Two mock servers in `tests/integration/connection.rs` assumed
  integer ids and now echo the id back unchanged.
- **Trace format v10.** `playwright-rs-trace` accepts 8 to 10. v10 drops
  `stepId` and nothing else changes shape. The fixture is regenerated on
  1.64 (`"callId":"wwyu@7"`); the 1.63 recording is kept as
  `basic-v9.trace.zip`, the same way the v8 one was, and a new test pairs
  actions on both id shapes. A numeric `callId`, which is what any client
  still sending integer ids gets back from a 1.64 driver (an older crate
  pointed at one through `PLAYWRIGHT_DRIVER_PATH` or `connect`, say), is
  read as its decimal string, so its events still pair instead of all
  becoming `Unknown`.
- This needs a `playwright-rs-trace` 0.2.1 release alongside 0.20.0, and
  the release commit must raise both `playwright-rs-trace` requirements in
  `crates/playwright/Cargo.toml` (the `trace` feature's dependency and the
  dev-dependency) from `0.2` to `0.2.1`. Otherwise a downstream lockfile
  holding 0.2.0 keeps it, and 0.2.0 refuses every trace the bundled driver
  writes. It cannot move before the version does: cargo does not fall back
  to crates.io for a path dependency whose requirement its own crate fails.

Gates, locally on macOS: the default lane (949 tests) is green after the
mock fix, the Firefox, WebKit and stress lanes (56 tests) are green, and
so are `verify-driver-version`, `sync-protocol-spec --check` and
`verify-protocol-methods`. Linux and Windows are CI's.

## Slice 1: credential sign counts

This is first because without it the bump loses data silently. 1.64 tracks
a virtual credential's signature counter: `credentialsCreate` takes an
optional `signCount`, `credentialsCreate`, `credentialsGet` and
`storageState` return it, and `newContext`, `launchPersistentContext` and
`setStorageState` restore it through the new `SetVirtualCredential` struct
(where it is optional and defaults to 0). Our `VirtualCredential` has no
such field, so serde ignores it on the way in, and a storage state saved
and restored through the crate restarts every counter at 0. A relying
party that checks counters rejects one that goes backwards, which is the
failure upstream added the field to prevent.

- `VirtualCredential::sign_count: u32` with `#[serde(default)]`, so a state
  saved before 0.20 still loads. The struct is `#[non_exhaustive]`, so the
  field is additive.
- `CredentialsCreateOptions::sign_count`, sent as `signCount`.
- Update `storage_state_round_trips_credentials_content` in
  `browser_context/state.rs`, which still asserts five fields.
- Port `test_should_seed_and_report_sign_count` into
  `tests/integration/credentials.rs`: a fresh credential reports 0, one
  seeded with 41 reports 41, two `navigator.credentials.get` ceremonies
  move it to 42 and 43 (authenticator data, a big-endian u32 at offset 33),
  and `get(id)` then reports 43. Add a storage-state round trip that
  asserts 43 survives `storage_state()` and `new_context` with it.

## Slice 2: `Locator::within` and `Page::get_by_ref`

Both are client-side selector construction; nothing new goes on the wire.

- `Locator::within(&self, parent: &Locator) -> Locator`. Upstream it is
  `parent.locator(this)`, which builds
  `` `${parent.selector} >> internal:chain=${JSON.stringify(this.selector)}` ``
  and throws `Locators must belong to the same frame.` when the frames
  differ. Our `Locator::locator` takes only a string, so this adds the
  `internal:chain` form as a crate-private helper. It does not check
  frames: `and_` and `or_` combine locators the same way without checking
  (upstream checks all three), and `within` follows them rather than being
  the one combinator that returns a `Result`; its rustdoc says the check is
  not made. It exists on `Locator` only, not on
  `FrameLocator`, `Frame` or `Page`.
- `Page::get_by_ref(&self, aria_ref: &str) -> Locator`, which is
  `self.locator(&format!("aria-ref={aria_ref}"))`, unquoted. It is page-only
  upstream because the server resolves a ref like `f1e3` to a child frame
  and honors `aria-ref` only as the first selector part. The `aria-ref`
  engine already existed in 1.63, and `AriaSnapshotMode::Ai` is already
  exposed.
- Tests, ported from python: the 3x3 table case
  (`cells.within(rows)` is all 9, `nth(1).within(rows)` is a2/b2/c2, `last`
  is a3/b3/c3, `within(rows.nth(2))` is c2, a non-matching child is 0, and
  `.within(rows).nth(1)` is b2), plus `get_by_ref` resolving `e2` and `e3`
  from an `ai`-mode snapshot.
- `locator!()` rejects an engine prefix it does not know, and its list
  (`css`, `xpath`, `text`, `role`, `id`, `data-testid`, `nth`, plus the
  `internal:` namespace) has no `aria-ref`, so `locator!("aria-ref=e2")`
  fails to compile today. Add it, with a compile-pass case, and release
  `playwright-rs-macros` 0.1.2 with 0.20.0 (the release commit raises the
  `playwright-rs-macros` requirement in `crates/playwright/Cargo.toml`, as
  for `playwright-rs-trace`).
- Found while porting the tests: the expect API has no list form of
  `to_have_text` (python's `to_have_text([...])`), so these tests compare
  `all_text_contents()`. That is an older parity gap, not a 1.64 one, and
  goes in the gap analysis rather than this release.

## Slice 3: `content` with shadow roots

`Frame.content` gained `includeShadow`, which serializes open shadow roots
as declarative shadow DOM. Changing `content()` to take options would break
its most common call, so this follows the crate's `*_with_options`
precedent: `Page::content_with_options` and `Frame::content_with_options`
taking a `#[non_exhaustive]` `ContentOptions` with `include_shadow`.
`content()` stays and sends no options.

Test, from python's `test_content_should_include_shadow_roots`: the default
strips shadow roots, `include_shadow(true)` returns the exact nested
declarative-shadow-DOM markup, and a closed root never appears. Cover the
page and its main frame.

## Slice 4: cookies on `APIRequestContext`

Three new methods, mirroring `BrowserContext`: `add_cookies` (sends
`addCookies {cookies}`), `cookies(urls)` (sends `cookies {urls}`, an empty
list for none, and unwraps `{cookies}`), and `clear_cookies(options)`. For
`page.request()` and `context.request()` they act on the browser context's
cookie jar. Python sends all three with no timeout.

`clear_cookies` takes `name`, `domain` and `path` as a string or a regular
expression, sent as `name` or as `nameRegexSource` plus `nameRegexFlags`
(and likewise for the other two). Our `ClearCookiesOptions` is string-only
and has been since 1.43, so `BrowserContext::clear_cookies` has the same
gap. Fixed once for both: the regex goes to the driver as JavaScript, so it
is a source and flags rather than a Rust `regex::Regex`, and each filter
gains `*_regex_source`/`*_regex_flags` fields set by a `name_regex(source,
flags)` style setter, the crate's `_regex` naming. That leaves the string
fields as they were, so the change is additive; setting either form of a
filter clears the other.

`Cookie` had no `url`, so a cookie could only be added by domain and path,
on `BrowserContext` as much as here, and python's tests add one by URL.
`Cookie::url` covers it; the driver rejects a cookie with a URL and a
domain or path, so empty ones are no longer serialized.

1.64 also changed `cookieMatchesClearFilter` to treat `""` as a real filter
(`value === undefined` replaced `!value`), so the setters must not send an
empty string to mean "unset".

Tests, from `test_fetch_global.py` and `test_fetch_browser_context.py`: the
`Cookie` header is `a=b; c=d` after `add_cookies`; `storage_state()` shows
the defaults (`sameSite` Lax, `expires` -1); a cookie with neither a url
nor a domain/path pair fails with `Cookie should have a url or a
domain/path pair`; `cookies` filters by no url, one url and several, with a
secure cookie on https; `clear_cookies` with no filter sends no `Cookie`
header afterwards, and with string and regex filters (`one\.com$`,
`^sess`) removes only the matches; on `page.request()` all three read and
write the browser context's jar.

## Slice 5: video and screencast options

- `RecordVideo::fps`, sent inside `recordVideo` (the other bindings expose a
  flat `record_video_fps` and fold it in; our `RecordVideo` struct already
  is the nested shape, so the field goes there). This applies to
  `new_context`, `new_page` and `launch_persistent_context`. The server now
  rejects `fps <= 0` with `"recordVideo.fps" must be a positive number`.
- `RecordVideo::show_actions`. Missing since 1.59, and the new `style`
  option lives inside it, so it lands here: duration, position, font size
  and the new `style`, with the same `ShowActionsOptions` shape the
  screencast uses.
- `ScreencastStartOptions::fps`, sent as `fps` on `screencastStart`; it has
  an effect only together with `path`.
- `ShowActionsOptions::style`, a `#[non_exhaustive]` struct of three CSS
  strings (`point`, `highlight`, `title`), sent as `style`.
- `ShowActionsOptions::font_size` becomes `#[deprecated(since = "0.20.0")]`
  in favor of `style.title`, per the deprecation convention in `CLAUDE.md`,
  except that it keeps being sent, because the driver still accepts it.
  Add it to the v1.0.0 removal list in the gap analysis.

The spec gate in `browser_context/options.rs` checks top-level option keys
only; extend it to the keys inside `recordVideo` while this is open, since
that is where both new keys live.

Tests, from `test_video.py` and `test_screencast.py`: a 60 fps recording
produces a file on both the context and the screencast paths; `fps(0)` and
`fps(-1)` fail with the server's messages (the Rust type should be
unsigned, which leaves only 0 to test); `show_actions` with a style still
lets a click complete.

## Slice 6: WebMCP

A new class, reached as `Frame::webmcp()` and `Page::webmcp()` (the page's
is its main frame's).

- `tools()` sends `Frame.webmcpTools` with no params (a timeout, if given,
  goes into the metadata envelope, which `send_message` already does) and
  returns `Vec<WebMcpTool>`: `name`, `description`, `input_schema` as raw
  JSON (`Option<Value>`, not a serialized value), and `annotations` with
  `read_only`, `untrusted_content` and `consequential`. The server omits
  absent fields and emits only true annotations, so every one is optional.
- `call_tool(name, input)` sends `Frame.webmcpCallTool {name, input}` with
  `input` through `serialize_argument`, and parses `{result}` through
  `parse_result`. A result with `isError: true` is returned, not raised.
  The result is typed through serde, as `Locator::evaluate` returns it.
  The input is a plain `&I` rather than an `Option`, so a tool with no
  input takes `&()` and nothing needs a turbofish (the driver substitutes
  `{}` for a null input): `evaluate`'s `Option<&T>` is exactly the CE2(b)
  problem, and this does not copy it. A timeout goes in `WebMCPOptions`.
- The landing page gets an `unreleased` "Agent tools (WebMCP)" card, with
  its snippet compile-checked by `verify-site-snippets` and its id in the
  site-e2e card list; the flag comes off at release.
- The landing page also publishes six tools of its own
  (`crates/site/src/agent_tools.rs`, registered from Rust through js-sys
  when the browser has WebMCP). Four only read it: `get_install`,
  `list_features`, `get_snippet`, and `list_versions`, each answering from
  what the page renders. Two change it the way a visitor's click would:
  `compare_with` switches the language comparison and returns both
  versions of the test, and `open_version` drives the version switcher,
  answering before it navigates (500 ms later, since the browser hands a
  result back after `execute` returns). site-e2e lists and calls all six
  and publishes the tool list as a receipt beside the trace; the
  walkthrough's step 7 shows an agent switching the comparison, checked
  with the same locators a click is. This works on GitHub Pages:
  the tools run in the visitor's browser, which only needs the secure
  context Pages already serves.
- `examples/webmcp_agent.rs` shows the loop for agent builders: a page's
  tools go to a model as they are, the chosen call runs through
  `call_tool`, and a page with none falls back to an `ai` snapshot and
  `get_by_ref`. It needs no model or key.
- Chromium needs `--enable-features=WebMCP` in `args`; Firefox needs the
  `dom.modelcontext.enabled` and `dom.modelcontext.testing.enabled` prefs
  through `firefox_user_prefs`; WebKit is unsupported and the server says
  so. Say all three in the rustdoc, with the error strings.

Tests, from python's new `test_webmcp.py`, with a test-server route for
`/webmcp.html` that registers two tools through `document.modelContext ??
navigator.modelContext`: tools sorted by name, with `add` carrying its
schema and `read_only` and `noop` carrying neither; the main frame's list
equals the page's; an empty page lists none; `call_tool("add", {a: 2, b:
40})` returns the text `42`; an `isError` result comes back as is; an
unregistered name fails with `No WebMCP tool named "missing"`. Chromium in
the default lane, Firefox in the Firefox lane, nothing for WebKit.

## Slice 7: behavior changes

- **Hidden iframes.** An element inside an iframe that is itself hidden now
  counts as hidden for actions, `is_visible()` and `to_be_visible()`
  (`frameSelectors.ts` carries `frameVisible` through each `enter-frame`).
  No existing test puts content in a hidden iframe, so nothing flips. The
  new test pins both paths, and they differ: through `frame_locator` the
  button in a hidden iframe is hidden, but through `content_frame` it is
  visible, because a frame used directly starts out visible and only a
  selector that enters the iframe carries its visibility. The changelog
  says so.
- **WebKit visibility** now uses the browser's native `checkVisibility()`
  rather than a `details`/`summary` workaround. That is a WebKit-lane
  watch item, covered by the lane run in slice 0.
- **VP9 video.** Output is still `.webm` and no test inspects the codec.
  Nothing to do.
- **Serialized errors** gained an optional `code` (a Node system error code
  such as `ENOENT`), and the server now appends ` (ENOENT)` to such
  messages. `ErrorPayload` ignores the field, and python does not surface
  it either. Leave it until someone needs to match on it.
- **Device descriptors** changed only their `userAgent` strings. 1.64's
  `screen` forwarding is a test-runner fixture and does not reach a library
  `new_context`. Separately, our `DeviceDescriptor` drops the `screen` that
  115 descriptors carry, and `BrowserContextOptions` has no `screen`
  option at all. That is a pre-existing parity gap, closed in slice 11.

## Slice 8: fixes python made in the same roll

playwright-python main fixed several serialization and validation bugs
alongside the roll. Each needs checking against this crate before it is
called a gap, so this slice is an audit, not a list of known defects:

- regular expressions round-trip through `evaluate` as `{"r": {"p", "f"}}`
  in both directions;
- `-0` survives serialization (python now detects it with `copysign`);
- `Page::pdf` turns numeric width, height and margins into `"Npx"`;
- `route.fulfill` with an empty JSON array or object still sets
  `application/json`;
- the fetch content-type check is case-insensitive; NaN and infinities in
  request data are rejected rather than sent;
- `Locator::screenshot` passes its timeout through.

A confirmed bug gets a failing test first, then the fix, and its own
`Fixed` entry. Done; two were real here, and the python test that found the
second named a third:

- regex results: real. `parse_result` had no case for `{"r": ...}` and
  returned `null`; a regex now reads as its `/source/flags` literal. Rust
  has no JavaScript regex type to send one the other way.
- `-0`: already serialized as `{"v": "-0"}`.
- `pdf` sizes: not applicable, they are `String`s here.
- `fulfill` with empty JSON: not applicable, `json()` always sets the
  content type.
- fetch data: not applicable, `FetchOptions` takes only raw `post_data`, so
  there is no content-type sniffing or JSON encoding to get wrong.
  `serde_json` writes NaN and infinities as `null` rather than invalid
  JSON, which is a silent conversion but no crash.
- `Locator::screenshot` timeout: passed through already, but python's test
  for it (a missing element times out) exposed a larger gap:
  `Locator::screenshot` did not wait for its element at all and failed at
  once with `ElementNotFound`. It now waits with `waitForSelector`
  (`attached`, strict), as upstream does.

## Slice 9: the Node pin

`driver_urls.rs` says the pinned Node must match the one playwright-python
commits as `NODE_VERSION` at the matching tag. playwright-python pins
24.21.0 at `v1.63.0` and on `main`; the crate pins 24.17.0, so it was off
its own rule under 1.63 already, and slice 0 missed it again. Move the pin
to 24.21.0.

The driver cache directory is keyed by Playwright version and platform
only (`cached_driver_dir`), so a machine that already assembled 1.64.0 with
Node 24.17.0 would keep it after the pin moves. Key the directory by the
Node version as well, and update `cached_driver_dir_is_keyed_by_version_and_platform`
to say so. Check `install`, the `ServerNotFound` message and the CI driver
cache keys (`pw-driver-*` in the three workflows) for anything else that
names the directory.

## Slice 10: the launch timeout

The crate sends 30 seconds as the timeout for `launch`,
`launch_persistent_context` and `connect_over_cdp` when the caller gives
none (`launch_options.rs` and `browser_type.rs`, through
`DEFAULT_TIMEOUT_MS`). playwright-python sends 180,000 ms for all three
(`DEFAULT_PLAYWRIGHT_LAUNCH_TIMEOUT_IN_MILLISECONDS`), and 1.64 corrected
Playwright's own docs to say 180 seconds. Add a `DEFAULT_LAUNCH_TIMEOUT_MS`
of 180,000 for those three and keep `DEFAULT_TIMEOUT_MS` for everything
else. `connect` stays at its documented 30 seconds (python sends no
timeout there, which is a separate question). A launch that hangs now
takes three minutes to fail, which goes in the `Changed` entry. Unit-test
the default each of the three sends.

## Slice 11: device `screen`

Not a 1.64 item, but a parity gap found while checking 1.64's device
changes. playwright-python's `new_context`, `new_page` and
`launch_persistent_context` take `screen` (the size `window.screen` and
media queries report, separate from the viewport), and a device descriptor
carries one in 115 of its entries. This crate has neither.

- `BrowserContextOptions::screen`, a `{width, height}` sent as `screen`;
  the spec gate in `browser_context/options.rs` already lists every
  context option key, so it shows whether `screen` was the only one
  missing.
- `DeviceDescriptor::screen: Option<DeviceViewport>`, read from the
  descriptor. The crate has no code that turns a descriptor into context
  options (callers copy the fields), so there is nothing else to carry it
  through; the field docs say to pass it as `screen`.
- Tests: a context with `screen(1920, 1080)` and a smaller viewport reports
  `window.screen.width` 1920 and `window.innerWidth` the viewport's; a
  device's descriptor reports its `screen`.

## Decisions

Settled 2026-10-11:

1. **Everything ships in 0.20.0**, the 1.64 API surface included, as
   "Playwright 1.64 Completeness".
2. **The launch timeout moves to 180 seconds** (slice 10).
3. **Device `screen` is implemented here** (slice 11).
4. **Node moves to 24.21.0** (slice 9), since the crate's own rule requires
   it.

## Out of scope

Test-runner and JS-only items: `testProject.default`,
`fullConfig.filteredProjects`, `--shuffle`, `test.describe.configure({lock})`,
`toHaveScreenshot` `type: 'webp'` in config, the `updateSnapshots`
`'missing'`/`'default'` change, JSX following `tsconfig`, the `screen`
fixture, and the `blob` reporter. `Tracing.start` returning a `Disposable`

`localUtils.asLocatorDescription`, which are `internal: true`.

## Order and gates

Slice 0 landed first, and nothing else starts until its CI is green on all
three platforms. The rest are independent of each other. The order is 9
and 10 (small, and they change what every later test runs on), then 1,
2, 3, 11, 4, 5, 6, 7 and 8, then the release. Each slice is one commit with its tests, a `CHANGELOG.md` entry,
rustdoc with the `See:` link, and a `metadata.version` bump on the skill
where it documents the new surface. Each runs `./scripts/mutants.sh` on its
branchy logic (the `within` selector builder, the clear-cookies filter
conversion, the WebMCP tool parsing), and `cargo xtask verify-agent-docs`
where the skill changes. The site's feature cards and snippets get a look
when slice 6 lands, since WebMCP is the headline of the release.
